# Jane desktop correspondence

Version 0.1.3 adds a separate desktop mailbox. The existing CBI CHAT remains the authored, state-triggered narrative system described in D-080. Mail never changes application state, character schedules or saved world canon.

## Use and delivery

An installed 0.1.2 companion receives this release through `检查在线更新` → `更新并重启`; no new ZIP, image download, runtime, login or routine credential is needed. The existing signed-core update format and pinned key are unchanged. The new core advertises `messageInset: 360`, expands the window above the character for the panel, and retains the resting location across close, drag and restart. Narrow artwork gets a usable 300px panel. Whole-pixel center offsets avoid repeated one-pixel drift. The core version in the initial URL bypasses stale HTML after restart.

The hosted page shows a small `留言` button, a scrolling history and a text box. A message saves on the server before attempting a Claude task. Sleeping/away Jane leaves it queued; when the companion is running and he is available, the existing subscription routine prepares a reply. An already started task can finish while the pet is closed. Queued work starts when a running pet checks again, not from a new always-on background scheduler. Incoming replies add an unread badge; a single character click opens unread mail, otherwise it retains the existing state/speech panel. Double-click still opens the selected installed application.

The client checks pending mail every five seconds, idle mail once a minute. Draft text, uncertain-send request IDs and the read marker remain local and account-scoped; accepted messages/replies persist on the server. Reloads and uncertain HTTP results reuse the same message ID, so retries cannot silently create duplicate paid tasks. Failed or expired runs remain visible and may be explicitly resent as a new message. An automatic or ambiguous task is never blindly refired.

As of 2026-11-19, manual messages also receive a variable wait before generation starts: roughly 15–90 seconds, 3–12 minutes or 15–45 minutes, plus the existing generation time. Reading/case states favour longer waits; relaxed activities favour shorter ones, with all three ranges possible within one activity. `reply_not_before` is sampled once and persisted in the dedicated mail row. Polls, duplicate sends and client restarts never move it. Mail left during sleep/absence gets timed on the first available check; being due never overrides the sleep/away gate. Manual queued mail retains priority over automatic letters. The UI shows the existing neutral waiting text without a countdown or claims about whether Jane has read it.

Apply `supabase/companion-reply-timing-schema.sql` before deploying both function entrypoints and the new `_shared/companion-timing.mjs` dependency. This is an additive nullable column; completed mail and existing application state are not migrated. No native-core update or replacement Windows package is needed.

Older cores keep status/speech working and show an update hint when the mailbox button is clicked. They do not start automatic companion tasks until the upgraded native capability is available.

## Model context and frequency

The existing configured `office-lines` routine channel carries `content_type: companion-message`, preserving saved worker compatibility. A per-run prompt specifies the result schema. It includes current saved Sacramento canon, ten-year continuity, Milo's male identity, the current deterministic Jane state, up to twenty-four completed exchanges and a bounded snapshot of recent shared records. It does not create a new Messages API account or use a new credential.

Only the new diet `calorie_log_db`, all six `wallet_accounts_v1.expenseBooks`, and SUITCASE cleanup/brought records are selected. The snapshot covers at most 24 records within the previous seven working days; the date boundary remains 04:00 JST. It excludes legacy diet, assets/balances, body logs, photos and unrelated private columns. The server reads with the verified caller bearer token and existing RLS, never the routine service identity. Account IDs supplied by the client are only compared against the verified identity, never trusted as authorization.

Shared records are framed as material Milo deliberately shared in this correspondence, not as Jane gaining screen-reading or general access to private information. The prompt distinguishes a log date from when an event just happened, does not equate missing logs with not eating, and disallows invented details, spending/calorie judgment and supervisory reminders. Jane responds in his existing light, clever voice, without narrating Milo's actions or resetting the established relationship. Model output is text-only and bound to the owner, message, canon revision and a whitelist of record fingerprints.

The 2026-11-19 follow-up explicitly confirms Milo as Jane's boyfriend in this correspondence. This local instruction follows the saved story context so older generic caution about unspecified relationship labels does not undo it. It does not add a marriage, exclusivity promise or old shared event. State remains authoritative for presence/timing and physical consistency; it is no longer a mandatory subject for a letter. Proactive topic nudges cover ordinary daily life, what Jane ate, what he wants to eat, date invitations, affection and small observations. Selection is independent of activity and discounts recently repeated subjects; it is a flexible writing direction, not a rotating template. Direct replies keep Milo's actual message first.

The user permits ordinary low-stakes details about Jane's own day. The longer conversation window preserves recently mentioned meals and plans; the prompt asks for consistency, rather than replaying the same lunch, discovery or invitation. Proposed dates await Milo's response and never write a schedule or assert his acceptance. This permission does not fabricate facts about Milo, other people's experiences, real employers, case events or past shared commitments. The prompt also removes the repetitive acknowledge/analyse/advise/question pattern and asks for familiar, clever boyfriend correspondence without turning every topic into books, casefiles, tea or the shark.

## Osaka weather in new correspondence

The bridge optionally reads current Osaka conditions from the same fixed city coordinates as the existing homepage, via Open-Meteo. It requests Celsius temperature/apparent temperature, WMO condition, precipitation, wind and day/night; Unix observation times avoid timezone ambiguity. A ten-minute process cache coalesces concurrent requests. Conditions older than 45 minutes, more than five minutes into the future, missing required fields or wrong units are omitted. Provider failures have a one-minute retry cooldown and do not interrupt mail. Only the winning generation run reads weather, after availability, delay, frequency and run-claim gates.

The weather service receives only public city coordinates and weather field choices: no auth credentials, correspondence, user records or precise location. The prompt receives a numeric/whitelisted summary with observation/fetch timestamps, not arbitrary provider text. This is Milo's real Osaka weather, separate from Jane's Sacramento/2006 setting. Jane may occasionally use it as a conversational opening; he should not infer that Milo went out, got wet or needs health/lifestyle supervision, and should not invent a later or next-day forecast. No GPS permission, client network-policy change, new database column, new Windows build or Claude credential is required. Current-weather API documentation: <https://open-meteo.com/en/docs>.

Automatic letters are at least 45 minutes apart and at most eight in 24 hours, and pause for at least 30 minutes after any correspondence. Only records actually referenced by a validated reply enter the mentioned-key set; later automatic letters omit those records. Letters deduplicate by owner/time bucket independently of state or unmentioned records, so choosing a daily-life topic does not permanently silence future mail on the same unused record keys. Manual messages take priority over automatic letters and share the original global one-active-run gate and six-starts-per-fifteen-minute budget. These are implementation defaults, not new world rules.

## Backend and validation

`jane_companion_messages` is a new dedicated server-only table. RLS is enabled, client/PUBLIC grants are revoked, and every Edge Function read/update scopes `user_id` from Supabase Auth. Existing records, schemas, grants and sync formats remain unchanged. Apply `supabase/companion-messages-schema.sql` and deploy both function entrypoints with `claude-companion.mjs`, `jane-companion-content.mjs` and their existing content dependencies. Deploy callback support before the bridge. Both functions retain their existing `verify_jwt: false` with in-function bearer/run-token authentication.

Tests cover queued-to-running-to-completed delivery, sleeping/away deferral, account and callback isolation, matching canon/record bindings, concurrent claims, ambiguous starts, expiry, deduplication, record selection, uncertain drafts, account ABA races, and the native panel's resting position. Browser QA uses only a fake account and fake delayed replies. Windows-native focus/relaunch and the subscriber's actual Claude callback are not exercised by the isolated preview.
